# NestJS Architecture

## Модульность
- Один модуль = один домен
- Каждый модуль: controller(s), service(s), при необходимости repository(s), плюс папки под типы/интерфейсы/DTO/схемы/entity
- API → Application → Domain → Infrastructure
- Контроллеры без бизнес-логики
- Сервисы без зависимости от контроллеров
- DB-сущности не выходят за пределы repository layer
- Composition over inheritance. DI через интерфейсы (символьные токены если нужно)
- Domain types не зависят от DTO. DTO не импортируют domain entities

## Стандартные роли (≈99% случаев)
В каждом домен-модуле ожидаются эти роли. Любая другая роль — обоснованное исключение, не норма.
- **module** — определение модуля и его DI-граф
- **controller** — HTTP/WS/gRPC-вход, без бизнес-логики
- **service** — бизнес-логика. Любой класс, делающий что-то предметное (внешний клиент, парсер, оркестратор, маппер) — это **service**, не "client"/"manager"/"handler"
- **repository** — единственная точка доступа к persistence. Никаких ORM-вызовов из service'ов в обход репозитория
- **entity** — ORM-сущности (TypeORM `@Entity`, MikroORM, Prisma generated, Drizzle table-types). Привязаны к persistence
- **schema** — описание структуры данных независимо от ORM (zod/joi/class-validator/Drizzle table definition). Schema ≠ entity: schema валидирует/типизирует на лету, entity — это row из БД с её ограничениями
- **model** — domain-объект/тип уровня бизнес-логики, persistence-агностичный. Между entity (БД) и DTO (API) — это слой
- **dto** — input/output для API-слоя
- **config** — инкапсулирует группу настроек (см. ниже)
- **module-private utilities** — допустимы как `*.util.ts` в `utils/` папке модуля или общем `common/utils/`, **только если они persistence-агностичны и не нуждаются в DI**

Реже: **gateway** (WebSocket), **processor** (BullMQ), **scheduler** (cron-only), **strategy** (Passport), **guard**, **interceptor**, **pipe**, **filter**. Если думаешь о такой роли — обоснуй.

## Naming файлов и классов
Один файл — одна публичная сущность. Имя файла отражает роль:

```
<feature-name>.<role>.ts
```

- Файл — kebab-case, роль — отдельный сегмент через точку
- Класс внутри — PascalCase + та же роль суффиксом: `UsersService`, `UsersController`, `UsersRepository`, `User` (entity)
- "Клиент внешнего API" — это `*.service.ts` с классом `*Service`. Слово `Client` в имени файла/класса не использовать
- Интерфейсы — `<name>.interface.ts`, тип/класс внутри — без обязательного префикса `I` (соблюдать project-level конвенцию). Default: `I`-префикс уместен для DI-портов и абстракций интеграций
- Типы и алиасы — `<name>.type.ts`
- DTO — `<name>.dto.ts`
- Schema (zod/joi/class-validator) — `<name>.schema.ts`
- Entity — `<name>.entity.ts`
- Config-сервисы — `<name>.config.service.ts`. Конфиг-интерфейсы — `<name>.config.interface.ts`

## Один файл = одна публичная сущность
- Один interface = один файл. Один тип-алиас = один файл. Один enum = один файл
- Допустимые исключения, **только когда сущности обязательно живут вместе**:
  - schema + её inferred-тип (`zod.infer<typeof xSchema>`)
  - entity + её relation-тип, если он автогенерится из ORM
  - связанная пара token + interface (`SOMETHING_TOKEN` + `ISomething`) — в файле интерфейса
- Группы однородных констант (DI-токены одного модуля, error-codes, event-names) допускаются в одном `<name>.tokens.ts` / `<name>.constants.ts`. Это не нарушение правила — это и есть одна сущность ("реестр токенов" / "набор констант")
- Не складывать в один файл несвязанные интерфейсы только потому что они "тематически близкие"

## Папки внутри модуля
Стандартный набор папок для группировки:

```
<module>/
├── dto/          — DTO
├── interfaces/   — порты, абстракции для DI
├── types/        — type-алиасы, доменные типы
├── schemas/      — валидационные схемы
├── entities/     — ORM entities (если используется ORM с entity-классами)
├── repositories/ — repository-классы (если их несколько; иначе плоский <module>.repository.ts)
├── utils/        — persistence-агностичные функции БЕЗ DI (если они есть)
├── <module>.module.ts
├── <module>.controller.ts
├── <module>.service.ts
└── <module>.repository.ts
```

Не использовать папку `models/` как корзину — она размывает границы между entity / dto / interfaces / types. Каждой роли — своя папка.

## Конфигурация
- **Все хардкоды (URL, headers, user-agent, page-size, timeouts, retry-bounds, feature-flags, секции БД) — в config-сервисы**, не в бизнес-сервисы
- Каждая внешняя интеграция / каждая группа связанных настроек = отдельный `*.config.service.ts`. НЕ один `AppConfigService` для всего
- ConfigModule инжектит env через zod-валидацию один раз и раздаёт типизированные config-сервисы остальным модулям
- Однотипные конфиги (например, конфиги внешних HTTP-API) реализуют **общий config-интерфейс** — это позволяет писать общие хелперы (HTTP-обёртки, retry, timeout) поверх абстракции, и единообразно тестировать
- Бизнес-сервис инжектит config-сервис как зависимость, не читает `process.env` сам. Если в сервисе появилось хоть одно literal-значение, относящееся к конфигурации — выноси
- Чисто алгоритмические константы (математика, regex для парсинга формата) могут жить в файле сервиса как `const`. Граница: если значение **может зависеть от окружения / провайдера / поменяется при добавлении новой реализации** — это конфиг

### Доступ к конфигу — через методы-бандлы, не через геттеры/свойства
- Config-сервис экспонирует **методы**, возвращающие логические бандлы значений, не отдельные геттеры на каждое поле и не публичные свойства
- Бандл = группа значений, которые **используются вместе в одной точке вызова** (всё для соединения с БД; всё для одного HTTP-запроса; всё, что нужно мапперу для построения ссылок)
- Сеттеров нет: конфиги read-only после инициализации
- Имя метода — `get<bundle-name>Config()` или `get<bundle-name>()`. Глаголами, как и любые методы
- Если значение действительно одно и не группируется (один API-ключ для всего сервиса) — допустим одиночный `get<value>()`. Граница: если рядом ≥2 значения, которые потребитель использует одной операцией — это бандл
- Общий config-интерфейс описывает методы бандлов на минимальном уровне; реализация может **расширять возвращаемый тип** (intersection / narrowing), чтобы добавить специфичные поля. Так разные интеграции делят общую сигнатуру (`getRequestConfig()`), но возвращают разный набор полей в рамках совместимого типа

## DI
- Constructor injection через `@Inject(TOKEN)` для интерфейсов, через тип-провайдер для классов
- Между модулями — через `exports`/`imports`
- Цикл — выделить третий module/service-only слой
- Symbol-токены для всех абстракций (`export const FOO = Symbol('FOO')`) — в файле интерфейса или в `<module>.tokens.ts`
- Module **никогда не экспортирует конкретный класс реализации, если этот класс — реализация интерфейса/порта**. Экспортируется токен. Потребитель внедряется по токену и получает абстракцию
- Группа однотипных провайдеров (массив реализаций одного интерфейса) собирается через **factory provider** — фабрика принимает уже зарегистрированные реализации и возвращает массив. Это позволяет:
  - добавлять новые реализации без правки множества мест,
  - инжектить группу одним токеном (`@Inject(STRATEGIES) strategies: IStrategy[]`)

## Однородность парадигм
- В пределах одного модуля не смешивать OOP/DI с чисто-функциональными модулями
- Если модуль состоит из сервисов под `@Injectable()` — внутренние помощники тоже сервисы (`@Injectable()`-классы), либо вынесены в общий `common/utils/` если они persistence-/DI-агностичны и переиспользуемы
- Файл-функция `<name>.parser.ts` / `<name>.mapper.ts` допустим **только** если: (а) функция чистая, без зависимостей, (б) не нуждается в конфиге, (в) не нуждается в логировании. Иначе — это `*Service`
- Парсеры HTML/JSON, нормализующие данные конкретного источника, нуждаются в конфиге (правила парсинга, селекторы, базовые URL для resolve-link) → почти всегда service'ы

## Lifecycle
- `OnModuleInit` — для setup, требующего DI-готового контекста (не блокирующая boot инициализация)
- `OnModuleDestroy` — для всего, что держит ресурс: HTTP-pool, DB-pool, WebSocket, child-process, файловые дескрипторы. Любое внешнее соединение должно иметь явное закрытие, не только `try/finally` — на жёстком kill `finally` не сработает
- `BeforeApplicationShutdown` / `OnApplicationShutdown` — для координации между модулями (например, дождаться завершения in-flight задач)

## Validation, ошибки, общая инфраструктура
- Глобальные `ValidationPipe`/`ZodValidationPipe` ставятся **до появления первого контроллера** — иначе валидация задублируется
- `ValidationPipe` с `forbidNonWhitelisted` молча роняет payload с лишними полями — добавь кастомный `exceptionFactory`, логирующий failed-поля и constraints, иначе дебаг вслепую
- Глобальный `ExceptionFilter` для consistent error response shape — в `common/filters/`
- Папка `common/` (или `shared/`) — pipes, guards, interceptors, filters, decorators, общие типы. Никакой бизнес-логики
- Внешние ошибки → domain-ошибки на границе модуля. В контроллер raw `Error('upstream timeout')` не выходит

## Внешние интеграции
- Каждая внешняя система (HTTP API, БД, очередь, scraper, LLM) — отдельный класс-сервис за интерфейсом
- Интерфейс описывает **порт** (что нам нужно), не публичный контракт системы
- Все настройки внешней системы — в её собственный `*.config.service.ts` за общим config-интерфейсом для интеграций такого же типа
- Никаких прямых fetch/axios/драйверных вызовов из домен-сервисов

## Готовность к расширению
- Прежде чем класть код в модуль, проверь: попадает ли логика в существующий домен или это новый модуль? Дробить заранее по доменам дешевле, чем разбирать "месиво" потом
- Если ожидается несколько реализаций (стратегии, провайдеры, store'ы) — сразу делать через интерфейс + factory provider, не хардкодить массив `[a, b]`
- Если ожидается несколько источников одного типа (внешние API, БД, очереди) — сразу делать общий config-интерфейс, чтобы добавление нового источника не превращалось в правку 5 файлов
